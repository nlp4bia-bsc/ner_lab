# Decision notes

Full rationale for the decisions whose reasoning does not fit on one line of
[DECISIONS.md](DECISIONS.md). Each section is the original row, verbatim: the decision as
stated, then the reasoning, evidence and rejected alternatives. The index row is the
authoritative statement of *what* was decided; this file is *why*, and it is never edited
after the fact except to strike a superseded section in place.

## D32

**`normalize_labels` defaults to `False` everywhere** (`read_annotations`, `read_ann`, `read_annotation_tsv`, `build_corpus`, `prepare_dataset`). A corpus keeps the labels its annotations declare. Normalization is opt-in.

Resolved 2026-08-07, superseding the original question of `metadata.json` precedence — that question dissolved once the direction of the rewrite was stated plainly. CARMEN-I's `.ann` holds `FARMACO` and its `metadata.json` declares `FARMACO`; the two agree, and the only thing overruling them was `LABEL_ALIASES`, a table inside this library. Renaming a corpus's own vocabulary by default is not ours to do. No metadata-precedence machinery and no rename warning are needed, because with the default off nothing is rewritten unless asked. Note normalization was never blanket reassignment — unknown labels pass through canonicalized (accents stripped, uppercased, `-`/space -> `_`); only the 13 alias keys are reassigned.

## D48

**The training orchestrator is `training/assessment.py::train_model`, task `train_model`.** No `pipeline/` package.

Closes Q5. Modelled on `transformers`, which this library follows by design intent: `pipelines` there means *inference* (`pipeline("ner")`), so a `pipeline/` package here would collide with the ecosystem's strongest naming convention. HF also does not name modules after architectural tiers — `trainer.py`, `training_args.py` sit next to what they orchestrate, and their "Repeat Yourself" philosophy rejects a layer that exists only to be a layer. `hpo/` will import this rather than share an orchestration package with it. The task name keeps `prepare_dataset`'s verb_noun shape and reads in pipeline order.

## D55

**The search space is Ray domains or a declarative mapping, interchangeably.** `build_search_space` merges `search_space` over `DEFAULT_SEARCH_SPACE`; a value may be a `tune` domain (passed through), `{"type": "loguniform", "low": ..., "high": ...}` (the YAML form), a scalar (pinned constant), or `None` (dimension removed). `variant` is reserved, built from `checkpoints`/`strategies`/`context_tokens`/`max_lengths`.

User decision. The declarative shape is what NER-API already wrote into its manifest — the converter is the inverse of code that existed, and `describe_search_space` round-trips it back for ours. Merge-over-defaults matches the D49 pattern for `training_arguments`; pin-and-remove is what makes a partial override usable. `effective_train_batch_size` stays searched with the micro batch derived under `max_micro_batch_size` (`resolve_batch_sizes`), as in NER-API: searching both produced duplicate experiments.

## D60

**The winner block is also written to `winner.yaml` in the sweep's run directory**, alongside its copy inside `hpo_summary.json`. `write_winner_config` is public.

D57 left the hand-off correct but manual: the block sits nested under one key in a JSON file, so reaching `train_model` meant hand-extracting a subtree and retyping ~18 keys — including the learning rate and batch resolution, where a typo silently changes the run and nothing catches it. The file changes nothing about the API: `train_model` still takes keyword arguments and never reads it, and `ner-lab run` reads any YAML. ~~`output_dir` is the sweep's own, so `ner-lab run <run_dir>/winner.yaml` lands the training run beside the sweep rather than inside it; `--output-dir` overrides.~~ **Amended by D77:** the emitted `output_dir` is now `<the sweep's own directory>/final_train`, because D77 removes the nesting this clause relied on. No file is written when every trial failed.

## D61

**Inference is `ner_lab/inference.py::predict_entities`, task `predict_entities`.** It takes a `model_dir`, not a run directory.

Closes Q8. The verb_noun shape of D48, reading in pipeline order after `train_model`. Pointing at the model rather than the run is what keeps inference independent of the orchestrator's artifact layout: a `fold_XX/best_model` and a directory copied to a cluster's scratch space load identically, and nothing has to know where the manifest that describes the run went. `--random-state` has no effect here and raises a `TypeError` if given — inference is deterministic, and D42 forbids an unused parameter kept only to satisfy a flag.

## D62

**A saved model carries an `encoding.json` beside its weights**, written by `train(model_encoding=...)` and built by `training.model_encoding`. It records the checkpoint, architecture and architecture kwargs, plus everything the `Encoder` was configured with. Output only — `train_model` never reads one.

User decision. Replaces NER-API's `best_config.json` -> `NERTrainingConfig` round-trip, which D49 removed, without pushing the encoding onto the caller: restating eight values where a wrong `max_length` silently shifts every window boundary is the failure `winner.yaml` had just been added to remove (D60). This is also the only thing that makes a CRF checkpoint loadable: `CRFForTokenClassification` is an `nn.Module`, not a `PreTrainedModel`, so `Trainer.save_model` writes a bare state dict with no `config.json` to rebuild the wrapper from. Precedent is HF's own `config.json` — the artifact describes itself. `train()` without it still saves weights; only a linear model can be reloaded from that.

## D64

**Per-span `score` and `text` are added to `evaluation/spans.py`**, not decoded again in `inference.py`. `bio_to_spans` takes optional `scores` and `text`, `predicted_spans` takes `texts` and `include_scores`, and `span_dataframe` keeps the highest-scoring copy of a duplicated span.

Discharges ROADMAP's baggage item: `03_infer_model.py` carried its own BIO-grouping walk because `metrics.token_bio_to_spans` had no score or text. Two implementations of B/I transition handling that must agree forever is exactly the duplication this migration exists to remove. Both additions are off by default, so the scoring path is byte-identical to what the evaluation checks already verify — a metric matches on offsets and never needed either field.

## D65

**The ten stage entry points are re-exported from `ner_lab` lazily, via a module-level `__getattr__`.** A name is top-level if it starts a stage or must be constructed to start one: `prepare_dataset`, `Encoder`, `build_model`, `training_arguments`, `train`, `train_model`, `build_compute_metrics`, `evaluate_predictions`, `search_hyperparameters`, `predict_entities`. Everything else stays at `ner_lab.<subpackage>`, and the long path keeps working unchanged.

Two rules, both measured. **Which names:** ~180 public names across six subpackages that are pipeline stages, so the folder structure carries meaning — the pandas/ray/optuna shape (114/49/25 top-level names), not the transformers one (6538, where the grouping lives in the name and the path is an implementation detail). Re-exporting everything would move the haystack, not remove it. **Why lazy:** `ner_lab/__init__.py` executes before *any* submodule, so a plain `from ner_lab.hpo.search import ...` would make `import ner_lab.data` cost ray + torch — 0.61s becomes 6.6s, and in an environment without torch it raises instead. Measured: `data`, `encoding` and `evaluation` pull nothing heavy today, and that torch-free half is worth keeping usable. With `__getattr__`, `import ner_lab` is 0.04s and imports nothing, `from ner_lab import prepare_dataset` stays torch-free, and only `train`/`search_hyperparameters`/`predict_entities`/`build_model` pull torch — because they are torch functions. Precedent is `transformers`, whose own `__init__` comment gives this exact reason ("without actually importing anything, and especially none of the backends"); verified here that `import transformers` leaves `torch` unloaded, as `import ray` does `ray.tune`. Cost, accepted: the ten names appear twice, in `_EXPORTS` and in the `TYPE_CHECKING` block that keeps editors and mypy working. Result dataclasses (`PreparedDataset`, `TrainingResult`, `AssessmentResult`, `HPOResult`, `InferenceResult`) are excluded — you never construct one, it arrives in your hands — as are the mutable defaults `DEFAULTS`/`DEFAULT_SEARCH_SPACE`/`HPO_ARGUMENT_DEFAULTS` (D32b's trap) and `multiclinner`, which D44 makes an option and never a default.

## D66

**The pretrained starting point is `base_model` (`base_models` where it is a sequence), never `checkpoint`.** Renamed on `build_model`, `build_linear_model`, `CRFForTokenClassification`, `train_model`, `model_encoding`, `run_directory_name`, `EncodedVariant`, `variant_key`, `build_variants`, `search_hyperparameters`, and in the `encoding.json`, `run_manifest.json`, `hpo_summary.json` and `winner.yaml` keys. The architecture contract of D35 is restated as `(base_model, label2id, id2label, **kwargs) -> model`. `checkpoint` keeps its HF meaning — the `checkpoint-*` snapshots the `Trainer` writes, `remove_checkpoints`, `best.checkpoint` — and is not renamed.

D27's one-name-per-concept rule, in the mirror direction: one name was doing two concepts. They collided in artifacts a user reads, since a single `train_model` run wrote `run_manifest.json` with `model.checkpoint` meaning the pretrained encoder and `training_summary.json` with `best.checkpoint` meaning a Trainer snapshot directory. `checkpoints=[...]` on the sweep read as a list of runs to resume rather than backbones to compare. `base_model` over the user's initial `base_model_path` because the values are usually Hub identifiers, not paths — HF names the underlying argument `pretrained_model_name_or_path` for that reason, README already documents it as "by hub name or local path", and a `_path` suffix would send a reader to download a model they can name; plural because in HPO it is a search dimension. Precedent for the term is PEFT's `base_model_name_or_path`, rejected in full only for length on a required parameter. Clean break with no compatibility shim: the user confirmed no trained model exists whose `encoding.json` carries the old key.

## D67

**`source_manifest.json` records `n_entities_by_label`**, a `{label: count}` mapping beside `n_documents` and `n_entities`, built by the public `data.count_labels(corpus)`.

User decision: a manifest that says a corpus holds 15064 entities without saying of what is not enough to pick a `target_label`, and the labels otherwise exist only inside per-row `entities_json`. Counts rather than a bare name list because the keys already answer "which labels" and the values answer the question asked next, while the sum cross-checks `n_entities` in the same file. No duplication of the balance report, which is per-partition, lives in the split directory and only exists when `split=True`; these are the corpus-level totals its rows sum to, and D23's caveat carries over — they count entities as annotated, before overlap resolution. Public per D26, since the alternative was making users call `parse_document_label_counts` and reduce a numpy matrix themselves; named `count_labels`, not `label_counts`, because `label_counts` is already a local name for that per-document *matrix* in `split.py` and `assignments.py`, and D66 was the cost of letting one name mean two things. **Consequence accepted:** `parse_document_label_counts` raises when a document's stored `n_entities` disagrees with its `entities_json`, so that check now also runs on the `split=False` and `source_parquet=` paths, which were previously permissive. Failing at prepare time on a corrupt corpus beats failing later, and a second lenient parser would be two implementations that can disagree. Cost is one pass over `entities_json`, computed once in `prepare_dataset`: measured 0.167s for 5000 documents holding 75000 entities.

## D68

**`gpus_per_trial` is removed from `search_hyperparameters`.** A trial reserves one GPU when `ray.cluster_resources()` reports any and none when it does not; there is no parameter. The resolved value is still recorded in `run_manifest.json`.

User decision: fractional and multi-GPU sharing should not be a top-level HPO knob, because someone who needs it should go into the library far enough to understand what they are changing. Hardcoding `{"gpu": 1}` was rejected once the consequence surfaced — the end-to-end sweep verification passes `gpus_per_trial=0` to run on a CPU-only machine, and an unconditional GPU request does not fail there, it makes Ray **wait forever** for a resource that never appears. Resolving from the cluster keeps the knob gone and the sweep testable. `use_gpu: bool` was the alternative, rejected as reintroducing the parameter to solve a problem detection already solves. The residual risk is a silent CPU downgrade on a misconfigured allocation, blunted by `smoke_test` running first (visible in seconds, not GPU-hours) and by the manifest recording what was resolved. The `gpus_per_trial > 1` raise dies with the parameter; the protection it described never lived there — `trial.require_single_device` is the real guard and stays, with its message reworded to stop naming a parameter that no longer exists.

## D69

**`DEFAULT_SEARCH_SPACE` searches `warmup_steps`, not `warmup_ratio`, over the same `uniform(0.0, 0.1)` range.** A pure rename: no range is re-derived.

transformers deprecates `warmup_ratio` (`logger.warning` on construction; its help text says "Use `warmup_steps` instead as it also works with float values"), and this library does not pin transformers, so the removal would land unannounced. The range survives untouched because `warmup_steps` is declared `float` and `get_warmup_steps` reads `< 1` as a proportion of total training steps and `>= 1` as an absolute count — the deprecation shim itself is a bare `self.warmup_steps = self.warmup_ratio` with no conversion. Verified against transformers 5.14.1 over 1000 training steps: `warmup_steps=0.06` gives 60, `0.1` gives 100, `1` gives 1, `50` gives 50, and legacy `warmup_ratio=0.06` gives 60 while storing `0.06`. The sweep therefore samples exactly the values it sampled before, and a winner block carrying `warmup_steps: 0.06` means the same schedule it always did. Documented in the README, since a fractional value under a `_steps` name is otherwise unreadable. Note transformers' own message says removal "in v5.2" while shipping the field at 5.14.1 — the version is stale upstream, which is a reason to migrate now rather than to trust the timeline.

## D70

**The dependency is `nvidia-ml-py>=12.0.0`, not `pynvml`.** `tracking.py` keeps `import pynvml` unchanged — the distribution was renamed, the module was not.

`pynvml` warns on import: `FutureWarning: The pynvml package is deprecated. Please install nvidia-ml-py instead.` Nothing else in the tree requires it, so it was ours to fix — of every installed distribution's metadata, only `ner_lab`'s asked for an NVML binding. The floor is not invented: `pynvml==13.0.1` itself declares `Requires-Dist: nvidia-ml-py>=12.0.0`, so this is the constraint every install already resolved under, minus the deprecated shim that shadows the real module's `pynvml.py` with a warning-emitting copy. Verified in a scratch venv on `nvidia-ml-py==13.610.43`: the module installs as `pynvml.py`, imports without warning, and provides all four calls `gpu_hardware_info` uses (`nvmlInit`, `nvmlShutdown`, `nvmlDeviceGetHandleByIndex`, `nvmlDeviceGetName`). `nvmlDeviceGetName` still returns `bytes`, so the existing `isinstance(name, bytes)` decode stays — no source change. A `uv pip install -e .` dry run resolves 111 packages with no conflict and no `pynvml`. No version floor above 12 despite `nvidia-ml-py` majors tracking driver generations (13.x is CUDA 13): the four calls predate all of them, and forcing 13 could mismatch a CUDA 12 cluster for nothing.

## D71

**Mixed precision is resolved per device, not fixed in `DEFAULTS`.** `default_precision()` picks bf16 where the GPU supports it, fp16 on pre-Ampere cards, neither without CUDA. Naming `fp16` or `bf16` in the overrides disables the resolution and takes the passed values verbatim.

`fp16: True` was never a decision — it entered with the script migration in `764044d` and no rationale was ever recorded. It is wrong on the hardware this library actually runs on. fp16's smallest normal is 6.1e-5 while transformer gradients reach 1e-9, so it needs dynamic loss scaling: an unscale-and-inf-check pass every step, discarded steps whenever the scale overshoots, and divergence if the scale collapses. bf16 carries fp32's 8-bit exponent, so none of that machinery exists; it pays 3 mantissa bits, which gradient descent tolerates far better than gradients rounded to zero. There is no speed trade to weigh against this — H100 and A100 tensor cores run fp16 and bf16 at identical throughput (989 and 312 TFLOPS respectively), so the expected gain is only the 1–3% of removed scaler overhead. A fixed default cannot be right for both, since bf16 needs SM 8.0 and V100/T4 lack it entirely. The cost accepted is that numerics now depend on the node, which a library producing a reproducible `winner.yaml` should not hide: both orchestrators already write `training_arguments.to_dict()` beside `gpu_hardware_info()` in the run manifest, so the resolved dtype is recorded next to the GPU that chose it. Secondary effect: `fp16: True` was invalid without CUDA, which is why every `verification/` script had to pass `fp16=False`; the resolution makes CPU runs work unaided.

## D72

**`ner_lab` ships `py.typed` and an `__init__.pyi` stub declaring the ten D65 exports.** The stub replaces the `TYPE_CHECKING` block, which is deleted; `_EXPORTS` and the runtime `__getattr__` are unchanged.

D65's lazy re-export defeats static analysis in the consuming project, which is where this library is used from. A module that defines `__getattr__` makes every attribute a type checker cannot bind statically resolve to `Any`, so `ner_lab.does_not_exist(1, 2, 3)` type-checked clean, and nothing outside the ten `TYPE_CHECKING` names — `ner_lab.data`, `ner_lab.hpo`, any typo — had a signature, a hover, or a completion. A `.pyi` takes priority over the `.py` for pyright and mypy, so the stub is the declared surface and `__getattr__` is invisible to them while the runtime keeps it. Verified with pyright against `import ner_lab`: `prepare_dataset` and `train` now reveal their full signatures and `does_not_exist` reports `reportAttributeAccessIssue`. `py.typed` is the separate half — the editable install resolves through a `.pth` outside the consuming workspace, so without the marker the package is a third-party library whose annotations a checker is not permitted to trust. Both files sit under `src/ner_lab/` and hatchling ships them with no `pyproject.toml` change (confirmed in the built wheel). No new duplication cost: the stub supersedes the `TYPE_CHECKING` block rather than joining it, so the ten names still live in exactly the two places D65 accepted, and the stub's `__all__` is asserted equal to the runtime's. D65's measurements are untouched — `import ner_lab` still loads no torch, and `from ner_lab import prepare_dataset` still does not.

## D73

**Public signatures are annotated where the type is unambiguous; the model factories are deliberately left bare.** `tokenizer` is `PreTrainedTokenizerBase` at all eight sites, the two Trainer/callback overrides match their base signatures, and `EpochMetricsLogger.__init__` / `build_summary` name their real types. `build_model`, `build_linear_model`, `resolve_trainer_class` and `train`'s `model` parameter stay unannotated.

Fallout from D72: with the stub in place, the remaining `Unknown`s were the ones the editor still could not help with. **Why the factories are excluded (user decision):** `build_model` returns a `PreTrainedModel`, or `CRFForTokenClassification` (an `nn.Module` and not a `PreTrainedModel`), or whatever a user's `Architecture = Callable[..., Any]` hands back, so the only true common supertype is `nn.Module` — and declaring it would promise something D44's pluggable architecture does not require. Bare is honest; `Any` would be the same information with more ceremony. **`TYPE_CHECKING` for the tokenizer import:** `encoding/` and `evaluation/` import no transformers at runtime, which is D65's torch-free half. Every module already has `from __future__ import annotations`, so the guarded import costs nothing; verified that `import ner_lab` plus all of `data`/`encoding`/`evaluation` still leaves both `torch` and `transformers` unloaded. **Two annotations exposed real mismatches, both upstream's.** `on_evaluate` returned `control` while the base's body is `pass` with no return annotation, which pyright reads as `-> None`; the returns were no-ops, since the method never mutates `control`, and `CallbackHandler.call_event` documents the skip ("A Callback can skip the return of `control` if it doesn't change it"), so they are removed and the method is `-> None`. That also closes a latent bug: the `scope="both"` branch calls `trainer.evaluate` in the middle, which reruns the callback handler and can reassign `Trainer.control`, and returning the stale object afterwards would clobber it. `Trainer.evaluate` annotates `eval_dataset` as `torch.utils.data.Dataset`, which `datasets.Dataset` is not a subclass of despite being the canonical input, so `train_dataset: Dataset | None` is kept and a `cast(Any, ...)` isolates the upstream defect to the one call. Verified: pyright reports exactly the 178 pre-existing errors, no new ones; `verify_training.py` passes 35/35; and `metrics_scope="both"`, which the suite does not cover, was exercised separately and still produces one eval and one train row per epoch.

## D74

**A document/annotation filename mismatch is reconciled by policy, not only by raising.** `resolve_mismatch(documents, annotations, on_mismatch)` is public and returns a `SourceMismatch` report; `build_corpus` and `prepare_dataset` take `on_mismatch: "error" | "documents" | "annotations"`, default `"error"`. `prepare_dataset` records the policy and both dropped lists in `source_manifest.json`.

Rule 3: a policy that drops the user's data carries an off switch, and the switch defaults to the strict behaviour — a missing `.txt` is usually a broken export, not an intentional subset. The two directions were asymmetric before: an `.ann` with no `.txt` raised, while a `.txt` with no `.ann` was silently kept with zero entities. `"documents"` keeps that asymmetry and only drops the orphan annotations; `"annotations"` makes the annotation set define the corpus, additionally dropping unannotated documents — a real behaviour change for that side, which is why it is opt-in. `"annotations"` still cannot keep an orphan annotation: there is no text for its offsets to refer to, so both non-raising policies drop it. The report is a return value rather than a `DataFrame.attrs` payload (no precedent in this library, and `attrs` propagation through `validate_corpus`'s copy is not guaranteed); `prepare_dataset` therefore resolves its own sources and hands `build_corpus` the aligned pair, which also reads each `.txt` once. Per D26 the behaviour is a callable users can drive themselves. A policy that would drop *every* document raises instead of returning an empty corpus, so the failure names the policy rather than surfacing as a cryptic error in the splitter.

## D75

~~**`train_model` refuses a multi-GPU allocation, and the guard is shared with HPO.** `require_single_device(arguments, allow_multi_device, context)` moves from `hpo/trial.py` to a new `training/devices.py`; both orchestrators call it. Default raises; `allow_multi_device=True` downgrades it to a banner-wrapped `RuntimeWarning` and proceeds.~~ **Amended by D78:** the move to `training/devices.py` stands and `require_single_device` still guards HPO trials, but `train_model` now pins rather than refuses, and `allow_multi_device` is gone. The mechanism analysis below is unchanged and is what D78 builds on.

A confirmed, silent regression, not a hypothetical. `hpo` pinned each trial to one GPU and asserted it; `train_model` accepted whatever the allocation gave it, so the sweep searched at batch 16 and the final training run on the same `--gres=gpu:4` allocation trained at 64. Measured on identical data and seed: `global_step` 11984 vs 2140, `training_loss` 0.0216 vs 0.2425, MultiClinNER strict F1 0.7781 vs 0.7571, and the sweep's own validation score for that configuration (0.7833) never reproduced on retrain (0.7588). The mechanism is `trainer.py:2453`, which wraps the model in `nn.DataParallel` whenever `n_gpu > 1`, reaching the larger batch by replication rather than by more steps — so steps/epoch fall by the device count and every step-denominated setting follows, including a fractional `warmup_steps` (0.3% of the run at 1 GPU, 17.7% at 4) and a cosine decay sized for a schedule 4x longer. **Why a guard and not a rescale:** deriving `per_device = effective // n_gpu` fixes the batch but not the schedule, since `num_training_steps` stays device-dependent; it also adds a does-not-divide failure and per-device OOM retuning. Pinning is exact. **Why it reads `torch.cuda.device_count()` and not `arguments.n_gpu`:** that is the identical call `training_args.py:1883` uses to set `_n_gpu`, so guard and Trainer cannot disagree — while `_n_gpu` is set at construction and survives pickling (verified), so a `TrainingArguments` that crossed a process boundary carries a stale count. **Why refusing and not silently setting `CUDA_VISIBLE_DEVICES`:** torch 2.10 re-reads the variable until CUDA initializes and caches it after (`if _initialized: _cached_device_count = r`), and `arguments.py:55` already initializes CUDA early via `is_bf16_supported() -> current_device() -> _lazy_init()`, so a library-side mutation would be probe-order dependent. A raise is order-independent. Placed after `resolve_training_arguments` so `use_cpu` is readable — the guard returns 0 there and on CPU-only machines, where the `DataParallel` branch is unreachable — and before encoding, model build and the manifest write. D68's note that `trial.require_single_device` is the real guard still holds; only its module changed.

## D76

**The run manifest records the device policy and `devices.effective_train_batch_size`.** ~~The policy field is `devices.allow_multi_device`.~~ **Amended by D78:** it is `devices.policy` plus `devices.trained_on`. `effective_train_batch_size(arguments, device_count)` is public and returns `micro x max(devices, 1) x accumulation`.

User decision, and deliberately scoped down from the finding that prompted it. The original claim — that the manifest could not explain a batch-64 run — no longer holds once D75 lands: `gpu_hardware_info()` already reports *visible* devices rather than the node's physical count (it reads `CUDA_VISIBLE_DEVICES` via `visible_gpu_ids()`), so `per_device_train_batch_size`, `gradient_accumulation_steps` and `hardware.gpu_count` were already all three factors, and D75 pins the third to at most 1. The field that actually earns its place is `allow_multi_device`, which is **not** derivable from anything: a manifest showing `gpu_count: 4` is otherwise ambiguous between a pre-D75 commit, a knowingly waived guard, and a bypass, and those warrant opposite responses — the first is a run to discard, the second is a deliberate throughput run. Recording it also makes the waiver durable, since the D75 warning only reaches stderr, which is exactly what is lost when a SLURM log is rotated. `effective_train_batch_size` comes along because the dict was already being edited and because `hpo_summary.json` records the same key under `sampled`, which turns winner-vs-retrain into a field diff instead of arithmetic the reader must know to perform. No `device_count` field: it would sit beside `hardware.gpu_count` differing only under `use_cpu`, and two near-identical counts in one manifest invite the misreading this was meant to prevent.

## D77

**`output_dir` is the run directory.** `run_name` is deleted from `train_model` and `search_hyperparameters`; both write into `output_dir` directly with nothing derived or nested. `claim_run_dir(output_dir, overwrite)` refuses a directory holding a `run_manifest.json` unless `overwrite=True`. The winner config emits `output_dir: <sweep directory>/final_train`.

User decision: follow HuggingFace, where `output_dir` is authoritative and `run_name` is only a tracker label. `run_name` was pure redundancy — `run_name="foo"` is exactly `output_dir=output_dir/"foo"` — so the simplification is deletion, not a third `flat=` parameter. Adding an opt-in was rejected as keeping the conflation being complained about: `run_name=None` meant "invent a timestamped name", never "do not nest", and there was no value meaning the latter. Deleting it also closes three defects at once: the collision with `TrainingArguments.run_name`, which both reach through `train_model` meaning unrelated things and which `DERIVED_ARGUMENT_KEYS` already had to filter; the unreachable `timestamp` parameter on `run_directory_name`, since stability is now the default and a timestamp is opt-in; and `run_name="/abs"` silently discarding `output_dir`, because `Path("/a/b") / "/etc"` is `/etc`. `run_directory_name()` stays public and exported per D26 — the old layout is `output_dir=root / run_directory_name(label, architecture, model)`, one call. **The overwrite guard exists because the timestamp was doing two jobs:** organizing, and guaranteeing uniqueness. Flat keeps the first and drops the second, so a rerun would replace the previous manifest, metrics and weights; HuggingFace overwrites silently there and is well known for it. `run_manifest.json` is the marker because both orchestrators write it first. It is checked **once, before any `mkdir`**, so a wrong path costs a second rather than GPU-hours, and once rather than repeatedly because every run fills its own directory as it goes — a later check would refuse `fold_02/` on account of `fold_01/`. Not defended against: another process writing into a live run directory, since re-checking at the end would only discard the compute that discovered it. **Why the winner config changed:** `winner_configuration` was passed the sweep's *parent* `output_dir` and relied on `train_model` inventing a child; with nesting gone that value would have scattered final-train artifacts across the user's top-level runs directory. `<sweep>/final_train` keeps the experiment one movable tree, and the overwrite guard makes it unique by construction — two sweeps cannot share a directory, so a second sweep raises before it writes a `winner.yaml` at all. No CLI change is needed: `cli.py:36` splats YAML keys as kwargs with no schema, so existing configs parse unchanged; the one intended behaviour change is that an old config on a multi-GPU allocation now raises under D75 instead of training at the wrong batch.

## D78

**`train_model` takes `devices: Literal[1, "all"] = 1` and pins to one GPU instead of refusing to run.** `apply_device_policy(arguments, devices, context)` joins `training/devices.py`: `1` reads `arguments.device` to resolve and cache `_setup_devices`, then forces `arguments._n_gpu = min(visible, 1)`; `"all"` keeps the banner-wrapped `RuntimeWarning` and returns the visible count. `require_single_device` loses `allow_multi_device` and its warning branch, becoming a pure raise, and stays the guard for `hpo/trial.py`. The manifest's `devices` block becomes `policy` / `trained_on` / `effective_train_batch_size`.

User decision, correcting the scope of D75. D75 read the constraint as physical when it is only a default: `nn.DataParallel` is gated by exactly one expression, `self.args.n_gpu > 1` at `trainer.py:2449`, and `n_gpu` is a plain property over `_n_gpu` that HuggingFace itself forces down three lines earlier at `trainer.py:487` ("Force n_gpu to 1 to avoid DataParallel as MP will manage the GPUs"). Pinning therefore uses the supported seam rather than a private hack, and it fixes the batch too, since `train_batch_size` is `per_device_train_batch_size * max(1, n_gpu)` at `training_args.py:1758`. **Why this beats the D75 remedy:** that remedy was `CUDA_VISIBLE_DEVICES`, which only works before CUDA initializes, and `arguments.py:55` initializes it early through `is_bf16_supported()` — so the fix D75 instructed the caller to apply was one the caller could only apply outside the process, in a launch script, by hand, on every call site. Worse, the failure was late: a sweep-then-train script raised *after* the sweep, having spent the GPU-hours. Pinning is order-independent, because `_setup_devices` is a `cached_property` and reading `arguments.device` first freezes it before `_n_gpu` is overwritten; nothing recomputes it from the visible count afterwards. `_setup_devices` also sets the device to `cuda:0` and calls `torch.cuda.set_device`, so the model lands on one GPU with no further work. **Why `Literal[1, "all"]` and not an `int`:** `Trainer` wraps with a bare `nn.DataParallel(model)`, whose `device_ids` defaults to every visible device regardless of `_n_gpu`, so `devices=2` on a 4-GPU node would make the batch accounting say 2 while replication spanned 4 — the exact silent-mismatch class D75 exists to prevent. Only 1 and all-visible are honestly reachable without subclassing `_wrap_model`, so the type admits only those, and an in-between value raises a `ValueError` naming `CUDA_VISIBLE_DEVICES` as the way to get it. **Why trials keep the raise:** a trial holds a one-GPU Ray reservation, so a second visible device means the reservation was bypassed and the sweep's accounting is already wrong; pinning would hide a broken cluster setup behind a run that looks fine. `train_model` is choosing, `hpo` is asserting an invariant, and the two want different functions.

## D79

**An annotation whose text disagrees with the document it points into is resolved by `on_conflict: "raise" | "rewrite"`, default `"raise"`, and the document always wins.** `resolve_conflicts(documents, annotations, on_conflict)` joins `corpus.py` beside `resolve_mismatch` and returns a `SourceConflict` report; `build_corpus` and `prepare_dataset` take the parameter, and the manifest gains `on_conflict` / `rewritten_documents` / `n_rewritten_entities`. `"rewrite"` keeps the annotated offsets and replaces the annotation's surface form with `text[start:end]`, warning once with the count and the affected documents.

User decision, completing D74. D74 reconciled *which files exist*; this is the case D74 does not touch — both files exist and their contents disagree. That case had four raise sites (`brat.py:190`, `corpus.py:225`, `corpus.py:269`, `overlaps.py:72`) and no switch at all. **Why the document is the only possible winner:** labels are assigned from character offsets alone — `tagging.py:33` tags a token by `token["start"] < entity["end"] and token["end"] > entity["start"]` — and the entity's `text` field never reaches the model. Storing the `.ann` surface form against unchanged offsets would therefore record one thing and train on another, so the `.ann` can only "win" by relocating the offsets to wherever its string occurs, which needs a search with ambiguous and absent cases. The user scoped that out: a `.ann` that cannot be trusted is the annotator's problem, not the library's. Rewriting the annotation to match the text is the one resolution that leaves the corpus internally consistent, so the three downstream raise sites stay strict and unchanged — after a rewrite a conflict cannot reach them. That also handles out-of-range offsets with no special case: `text[start:end]` truncates and `_validate_entities`' `end <= len(text)` check raises, so `"rewrite"` cannot quietly produce a corrupt corpus. **Why a separate resolver rather than a branch in `_build_entities`:** D74's precedent — `prepare_dataset` resolves its own sources and hands `build_corpus` an already-clean pair — and `build_corpus` returns a bare DataFrame with no channel for a report. **Why `"raise"`/`"rewrite"` and not D74's `"error"`/`"documents"`:** the pair names actions and stays parallel; only one source can ever win here, so naming the winner would carry no information. Rule 3: the policy that edits the user's data is opt-in, and it warns when it fires.

## D80

**`on_conflict` gains a third value, `"drop"`, which removes every document carrying a conflict together with all of its annotations, and `resolve_conflicts` now returns `(documents, annotations, SourceConflict)`.** `SourceConflict` gains `dropped_documents`; the manifest gains `dropped_conflicting_documents`. `"drop"` warns once with the document count, the annotation count and the affected filenames, and raises if it would empty the corpus — the same guard `resolve_mismatch` already carries.

User decision, extending D79. D79 gave a corrupt export two exits, raise or rewrite, and rewrite is only correct when the offsets are trustworthy and the `.ann` string is the stale half. When the offsets are the drifted half, rewriting mislabels a span rather than fixing it, and the user's only remaining option was to repair the export by hand. Dropping the file is the third honest answer: a smaller corpus that is entirely trustworthy. **Why the whole document and not just the conflicting annotation:** dropping the offending row alone leaves a document that reads as fully annotated while a real entity is silently absent, which trains the model to predict `O` over that span — worse than not seeing the document. The corpus is the unit of trust, and D74 already drops whole files rather than parts of them. **Why the return signature changed:** dropping a file must remove it from the document set as well, and a report the caller has to remember to act on is a footgun — every caller that forgot would write a corpus containing the conflicting documents with their annotations stripped, the exact failure the previous paragraph rejects. Returning the resolved pair mirrors `resolve_mismatch` and leaves both resolvers reading identically at their call sites. Breaking change to an exported function, taken while there is one release and no external caller. **Why `"drop"`:** parallel with `"raise"`/`"rewrite"` as a verb naming the action; `"ignore"` was rejected because it reads as "ignore the conflict and carry on", i.e. no drop at all. Rule 3 holds: the default still raises, and the policy that discards the user's data is opt-in and warns when it fires.

## D81

**`data/stats.py::compute_text_stats`/`compute_annotation_stats` are a sibling step to `prepare_dataset`, not a parameter on it.** Both take `base_model: str` and load `AutoTokenizer.from_pretrained(base_model)` internally, never a loaded tokenizer object. `compute_text_stats` additionally takes `language: str`, mandatory like `Encoder`/`split_into_sentences` (D33) — the canonical corpus has no per-document language column, only a manifest-level one, so no groupby-by-language/`ALL`-row machinery survives from the source script. `cli.py::run` gets its first task-specific branch: for `task: prepare_dataset`, YAML keys `stats: "none"|"text"|"both"`, `base_model`, `language`, `normalize_labels` are popped before the call and, if `stats != "none"`, drive the two functions over `result.corpus`, writing `text_stats.{json,parquet}` (+ `annotation_stats.*` for `"both"`) into `result.dataset_root`.

User decision, migrating a standalone multi-language analysis script. **Why `base_model: str`, not `tokenizer: PreTrainedTokenizerBase`:** rejected the leaf-function precedent (`Encoder`, `tokenize_document` all take a loaded object) because that precedent is about tokenizer-consuming code reachable only by someone already elbows-deep in the library; these two functions are the simplest-script entry point the migration exists to serve, matching `train_model`'s `base_model` (D66) rather than `Encoder`'s. Named `base_model` over `tokenizer` once framed as 2-vs-1: consistency with the rest of the library's naming plus honesty about what is actually passed (a hub id/path, not a tokenizer) both point the same way. **Why no `stats` parameter on `prepare_dataset` itself:** keeps `data/dataset.py` and `data/stats.py` mutually unaware, matching D22's "stages are siblings, nothing forces chaining" — a plain Python caller wanting both still calls both. The CLI is the one place already allowed to know about multiple stages for one YAML file (D12), so the combining glue lives there instead, even though it costs `run()` its previously fully-generic `task(**parameters)` shape. **Why the source script's per-language grouping is dropped:** confirmed the script's original job was a multi-language directory scan; `ner_lab`'s canonical `documents.parquet` is single-language per corpus by construction (D33's rationale extends here), so grouping by a column that does not exist would not have worked at all, not just been unneeded generality. `PYSBD_LANGUAGE_MAP` (pysbd's missing cz/ro/sv rules) is also dropped: `Encoder` hits the same pysbd gap via the same `split_into_sentences` call with no such mapping, so adding it only in `stats.py` would fix the symptom in one of two call sites and leave the library inconsistent about which languages its own sentence segmentation covers. The driver's markdown rendering and directory-scanning `main()` are not ported; the two compute functions return DataFrames only, and the caller decides what to do with them, per D14.
